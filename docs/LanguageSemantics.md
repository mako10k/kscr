## 1. Language Overview

The language is designed for functional programming with default lazy (thunk-based) evaluation. All expressions are evaluated only when their values are required (call-by-need). Purity is enforced by default; side effects are only possible via explicit effect types.

### String Type

- **String (MVP)**: Strings are currently a primitive runtime value.
- String literals are written in double quotes, e.g., "hello".
- Future direction: represent strings as `[Char]` / or a dedicated internal structure (e.g. ropes) once list/substring performance and stdlib needs justify it.

### Type Aliases

- Type aliases (e.g., `type String = [Char]`) are compile-time only and do not change runtime representation.
- The type checker expands aliases as needed; errors may be reported using either the alias name or its expanded form.

### Numeric Types, Internal Lowering, and Checked Casts

- **Surface numeric types (MVP)**: `Integer` (arbitrary precision) and `Float64` (IEEE-754 binary64).
- Backend-interoperability cast targets include `i32`, `i64`, `f32`, and `f64`.
- Conversions that can lose information are checked at runtime; out-of-range integer casts and float overflow raise runtime errors.

## 2. Semantics and Evaluation

- **Lazy Evaluation**: All values are represented as thunks. Evaluation is deferred until the value is demanded. Memoization ensures each thunk is evaluated at most once.
- **Purity Principle**: All user-defined functions and expressions are pure by default. Side effects (such as IO, mutation) are not permitted in pure code.
- **Explicit Effects via IO Type**: Side effects are modeled explicitly using the `IO` type constructor.
- **Program Entrypoint**: `main` must typecheck as `IO _` (for some result type). The runtime evaluates `main` to an IO action and executes it.
- **Monadic Composition**: Effectful computations are composed using monadic operations. The language provides syntactic sugar (do-notation) for sequencing `IO` actions, similar to Haskell's `do` notation.
- **Effect Isolation**: Pure and effectful code are strictly separated by the type system. Only code within the `IO` monad (or other effect monads) may perform side effects.
- **Order of Effects**: The order of side effects is determined by the structure of the monadic composition, not by the order of evaluation of expressions.

### Example (do-notation)
```
do {
	x <- readLine;
	stdoutWrite x
}
```
This block represents a sequence of `IO` actions: reading a line, then printing a value. Each action is an `IO` computation, and the result is composed monadically.

## 3. List Comprehension

- **List Comprehension**: List comprehensions are syntactic sugar for generating lists. Multiple generators, bindings, and guards are supported.
- **Lazy Generation**: Lists generated by comprehensions are constructed lazily; elements are computed only as needed.
- **Semantics**: The form `[ expr | pat <- list, guard, ... ]` is interpreted as a combination of map, filter, flatMap, etc.
- **Example**:
```
[ x * x | x <- [1,2,3,4,5], x == 2 || x == 4 ]
```
This example lazily generates a list of squares of `2` and `4`.

---

## 4. Pattern Matching (Semantics)

- **Pattern Matching**: Deconstructs values according to their structure. Supports tuples, lists, records, data types, and more.
- **Wildcard/Variable/Hole**: Wildcards match anything, variables bind values, holes defer pattern resolution.
- **Or/View Patterns**: Or-patterns match alternatives; view-patterns apply a transformation before matching.
- **Strict vs Loose Record Patterns**: Strict matches all fields exactly; loose allows extra fields.
- **Match Failure**: Non-exhaustive matches result in runtime errors unless handled.

---

## 5. Program Structure

- The program entrypoint is `main`, and it must typecheck as `IO _`.
- Partial application and higher-order functions are supported throughout.
- Indent-based grouping is used for code blocks (see `TypeSystem.md`).
