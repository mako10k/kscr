## Investigation Notes

### Why the 6 tests fail

The tests fail because dict-lambdas are created in nested contexts but not auto-applied. Example from `ir_run_main_rational_smoke`:

```kscr
add (Rat a b) (Rat c d) = 
  let num = a * d + c * b;  -- (* creates dict-lambda here)
      den = b * d;           -- (* creates dict-lambda here)
      g = gcdLoop absN absD
  in Rat (__quotInt n1 g) (__quotInt d1 g)  -- fails: g is dict-lambda, not Integer
```

The pattern vars `a`, `b`, `c`, `d` are Integers, but `*` can't resolve to Integer Num instance at compile time because pattern vars don't have entries in the inferred type map. So `a * d` becomes `lambda __dict_Num -> ...`.

### Attempted fix: auto-apply in force_value

Tried adding auto-apply logic to `force_value` for Num/Eq/Show classes only. This caused 19 test failures because it auto-applied dict-lambdas that were intentionally being passed around as values.

### Next steps options

1. **Improve compile-time resolution**: Make pattern vars have their types available in the inferred map so `resolve_method_dict_expr` can find concrete instances
2. **Add more auto-apply sites**: Identify specific contexts (if expressions, nested applications) where auto-apply is safe
3. **Selective force_value auto-apply**: Only auto-apply in `force_value` when the value is about to be used in a primitive operation
4. **Accept limitations**: Document that pattern vars in arithmetic may need explicit type annotations
